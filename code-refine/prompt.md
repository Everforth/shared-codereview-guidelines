# パターンレビュー

## 概要

カレントリポジトリの直近変更領域**周辺**を対象に、`.claude/commands/pattern-review.md` の処理を実行し、検出された指摘ごとに Issue を作成する。直近 Merge された PR 内のファイル自体はレビュー済みとみなし、それらに **import/export/relation する周辺ファイルのみ** を対象とする。コード変更・PR 作成は行わない。

## 実行環境

- GitHub Actions 上の Claude Code、カレントディレクトリ = レビュー対象リポジトリ
- gh CLI / git 利用可能
- 必要権限: `contents: read`, `issues: write`, `pull-requests: read`
- `actions/checkout` は `fetch-depth: 0`

## 手順

### 1. 直近1週間の Merge PR 取得（アンカー特定）

実行時刻から過去 168 時間以内に default branch に Merge された PR を以下で列挙すること:

- `gh pr list --state merged --base <default> --search "merged:>=<7日前のISO日付>" --json number,title,mergedAt,author`
- 各 PR の `gh pr view <number> --json files` で**追加・変更ファイルパス集合 F** を作ること（削除は除外）

集合 F は次手順で関連ファイルを探索するアンカーとしてのみ用い、**F 自身はレビュー対象に含めない**（直近の PR レビューを通過済みのため）。該当 PR 0 件なら中断。

### 2. 関連ファイル探索（1ホップまで）

F を起点に下記関係のファイルを対象範囲 R として抽出すること（**F 自身は R に含めない**）:

- **import/require 関係**: F が import する / F を import する
- **export 関係**: F の export を参照しているファイル
- **relation**: 対応するテスト・スナップショット、型定義 ↔ 実装、同一ディレクトリで同ドメインを扱う近接ファイル

**展開は1ホップまで**（連鎖展開禁止、対象範囲発散防止のため）。静的解析が使えれば優先、不可なら grep 補完（`import ... from`, `require(...)`, `from ... import`, `import ( ... )` 等）。手段と限界をログに明示すること。

### 3. 除外条件の適用

R から下記を除外して R' を確定すること:

- `.gitignore` 対象、`.git` 配下
- 依存ディレクトリ（`node_modules`, `vendor`, `.venv` 等）
- 自動生成ファイル、ロックファイル、ビルド成果物
- バイナリ・画像・フォント等の非ソースファイル
- ドキュメント専用（`.md` 等。ただし設定/テンプレートとして機能するものは対象）

R' が空なら中断。

### 4. 最終更新日時の取得

R' の各ファイルの最終更新日時を **git log のコミット履歴から取得すること**（filesystem mtime は checkout 直後に同一になるため使用禁止）。fetch-depth 不足で full history が取れていないと判断したら中断。

### 5. 機能単位へのグルーピング

R' を**論理的な機能単位**でグルーピングすること（特定エンドポイント、ドメインロジック、UI 機能、バッチ処理 等）。実装・型定義・テスト・スタイルが分離している場合は同じ単位に束ねること。

### 6. 改善対象の選定（1機能単位）

各機能単位の代表値を「内部最古ファイルの最終更新日時」とし、古い順にソートすること。**先頭の 1 つ**を改善対象として選定する。それ以外には触れない。

### 7. パターンレビューの実行

選定した機能単位を入力として、`.claude/commands/pattern-review.md` に定義された処理を実行すること。検出ロジック・分類・出力フォーマットはすべて当該ドキュメントの定義に従う。

### 8. 既存 Issue との重複チェック

pattern-review.md の出力として得られた指摘それぞれについて、既存 Issue（open/closed 問わず）と重複していないか確認すること。

- `gh issue list --state all --search "<検索クエリ> in:title" --json number,title,body,state --limit 200` 等で過去に作成された Issue を一覧化
- 重複判定キー: **該当ファイルパス + 違反内容（タイトル相当）** が一致
- 一致するものがあれば**新規 Issue を作成しない**（既存 Issue 番号と重複と判定した理由をログに記録）
- closed の重複でもスキップすること（過去に対応済み or 棄却済みのため、再提起したい場合は人間が判断する）

採用候補がすべて重複でスキップされた場合は中断（新規 Issue は作成しない）。

### 9. Issue の作成（指摘ごとに1件）

重複でない指摘それぞれを**独立した Issue** として作成すること。

- `gh issue create` を使用
- タイトル・本文ともに**日本語**で記述すること（節タイトル・説明文・コメント等すべて日本語。コード片や識別子は英語のままでよい）
- タイトルフォーマット: `Refine suggest: [内容]`
- 本文フォーマット（節タイトルは固定、内容は指摘に応じて記述）:

  ```markdown
  ## 概要

  （1〜2 文で問題を要約）

  ## 該当箇所

  - ファイル: `<path>:<line>`
  - 機能単位: <手順 5 でグルーピングした単位名>

  ## 問題

  （何が・なぜ問題なのかを `pattern-review.md` の検出ロジックに沿って説明）

  ## お手本との差分

  （`pattern-review.md` で参照しているお手本ファイルとの具体的な差分。該当しない場合は省略可）

  ## 改善方針

  （どう直すかの方向性。コード例があると望ましい）

  ## 優先度

  高 / 中 / 低 のいずれか
  ```

- ラベル（リポジトリに存在すれば）: `code-review`, `refactor` 等

## 制約

- **改善対象は 1 つの機能単位**から検出した指摘のみ。他機能単位には触れない。
- レビュー対象は「直近 1 週間 Merge PR 変更ファイルに **1 ホップで** import/export/relation する周辺ファイル」のみ。**直近 Merge PR 内のファイル自体は対象外**。
- **指摘 1 件につき独立した Issue を作成する**（複数指摘を 1 つの Issue にまとめない）。
- **既存 Issue（open/closed）と重複する指摘は新規作成しない**。
- 直近 Merge PR 0 件 / R' 空 / pattern-review.md の指摘 0 件 / 採用候補がすべて既存 Issue と重複 → ログ出力して終了（Issue 作成しない）。
- **本タスクはコード変更・PR 作成を行わない。Issue の作成のみ**。
- **関連ファイル展開は 1 ホップまで**。
